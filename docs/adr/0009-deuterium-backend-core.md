# ADR 0009：Deuterium 后端重写与 Core 边界

日期：2026-09-08。状态：按本任务明确要求实施；语言和内部拆分为本次工程选择，性能收益待实测。

## 依据与覆盖

用户要求按 App／网页契约开始重写后端，允许导入旧 App 账密，统一为 Deuterium ID；将多服聊天、物品库与受控游戏能力收敛为 Deuterium Core；后端最终在 Linux，游戏服仍在远端 Windows。**本任务后续明确纠正：邮箱保留独立插件，不并入 Core；由用户按本任务给出的字段和时序修改邮箱。**

此决定覆盖 ADR 0004 的 Kotlin 后端、Windows 交付限制，以及旧文档的单服范围。Android 产品、玩家 UUID 权威、经济系统权威不变。主契约仍为 `/api/v1`，不能因实现用 Go 再造一套 App／Web 业务模型。

本工作区独立于正在修改的 App、网页和旧后端硬化工作区：`C:/DeuteriumAPP/.worktrees/backend-rewrite`，分支 `codex/deuterium-backend-rewrite`。旧源码保留用于迁移和协议核对，新服务目录为 `backend-next`。

## 部署与技术

采用 Go 标准 HTTP 服务、显式 SQL 和 MySQL/MariaDB，单个模块化进程；不先拆微服务，不强制引入 Redis、消息队列或 ORM。身份、聊天、商城、市场、委托、更新各自维护业务边界。Linux 交付可执行文件、systemd 单元和配置模板，反向代理终止 HTTPS/WSS。后端数据库放在后端可信网络。

游戏节点上的 Core 主动连 `wss://<api>/bridge/v1/connect`；Windows 不增加公网 HTTP 管理端口。每个节点独立凭据、固定 serverId、能力白名单，禁止远程任意命令、任意 SQL 和客户端指定 UUID。首期后端明确为单实例；多实例须增加节点租约、共享限流及跨实例订阅设计后开放，不能直接水平复制进程。

核心聊天与经济受控调用不依赖同机路径、Windows 启动台或 Venus。OSS 承载客户端直传图片；业务 API 只授权、验证对象、写业务记录，沿用最新 App 要求。

## 两种身份

- Deuterium ID 是稳定账号主体，首期沿用旧 `app_users.id` 为 `userId`，不因改名、QQ 修改或新增应用变化。
- Minecraft 身份为经可信游戏节点确认的 UUID。资产、发奖和玩家目录使用此绑定；未来非游戏应用使用 `userId`，不得把 QQ、游戏名或临时 playerRef 当成统一账号主键。
- 同一游戏 UUID 只能绑定一个主体。名称／QQ 冲突拒绝迁移，不自动合并。旧会话、旧验证码、管理员权限不自动导入。
- 第一方 App 与同域网页共享认证服务；未来独立应用使用同一 IdP 的 OIDC Authorization Code + PKCE。第一方并不是取消 OIDC 的理由；OIDC 是协议，不是第二套账号库。首个实现里程碑不冒充完整 OIDC Provider。

## Deuterium Core 的职责

Core 是统一的游戏侧入口和 API，不是把 NeoForge 的物品反序列化塞进普通 Bukkit 插件。结构分为：纯 Java 契约、Bukkit/Youer 插件、必要的 NeoForge 适配层。游戏现状是 Youer／1.21.1，应以 Java 21 与实际适配能力验证，不继续盲用 1.20.1 假设。

Core 统一提供节点身份、全网玩家位置、公共聊天、物品模板快照、经济受控操作、同步就绪适配信号和执行审计。**邮箱的存储、客户端显示、附件解码、领取和撤回全部保留在独立 Deuterium-Mail 项目。** Core 只包含调用邮箱公开 API 的适配器，不复制邮箱实现、不接管邮箱数据库、不另建收件箱。用户负责按对接契约修改邮箱，本任务不修改其项目。

后端管理账号、商品、订单、资金编排、申诉和前端通知。Core 管理原始游戏物品、物品模板版本和受控调用；独立邮箱管理邮件领取与背包副作用。XConomy/Vault 仍是余额权威，不因为后端重写复制一套余额。

独立邮箱负责其游戏侧共享 MySQL 的邮件和领取日志；Core 维护自己的桥接执行日志，通过邮箱 API 调用，不能直接读写邮箱表。它们与 Linux 业务库之间以持久化命令和事件通信，不做跨机双写事务。Redis 只可作为游戏集群通知加速器，不能决定邮件或领取是否存在。

## 一次交付必须能说清发了什么

管理端从 Core 已发布的不可变物品版本选择附件。商品保存发货模板引用；成交冻结模板版本、各附件数量、内容摘要、领取服务器明确名单和订单摘要。改商品／物品库不会改变已付款订单。原始 NBT／组件由 Core 保存并校验 SHA-256，后端只存安全元数据及指纹。

创建邮件的幂等键是稳定的 deliveryId，执行指令另有 operationId。同 ID 不同内容返回冲突，不能覆盖。领取与撤回在游戏共享库内互斥。只能在权威确认 REVOKED 后退款；CLAIMED 不可退款，UNKNOWN 必须查询原记录或人工核对，不能直接再发一次或当成没领。

本服总开关、邮件 serverId 白名单、背包共享域、物品兼容性、玩家当前会话与同步就绪全部通过才领取。Login 禁领；Amiya/Odyssey 按已确认政策候选可领；MEK 暂禁领。白名单发送时展开，新增子服不自动得到旧邮件权限。

## 可靠性与占用

数据库约束和事务负责跨请求一致性；事件入库后确认，断线重投去重；慢连接用有界队列并断开，让客户端补查。敏感操作超时保留 UNKNOWN，不靠进程内集合声称幂等。密码继续使用内存困难哈希，以有界并发限制占用，不能通过降低密码安全性换取省内存。

性能目标是可测量的开发目标，不是承诺：先报告空闲 RSS、身份接口延迟、聊天吞吐和 SQL 连接数；另做并发密码登录压测。没有同硬件、同数据、同负载的新旧对比，不写“比旧版快多少”。
