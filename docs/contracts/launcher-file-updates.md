# 启动器文件级增量发布候选

2026-10-15，未部署。用户本轮优先优化启动器结构、体积、更新器及全量下载；保留原账号、业务数据、配置与已有更新校验。本候选不新增 Windows 发布者签名，不改游戏通行和资源版本。

## 协议和旧版兼容

发布 JSON 可继续是原有协议 1 签名信封，也可为 `{schemaVersion:2, legacy:<协议1信封>, incremental:<协议2信封>}`。两个信封分别签名，并且版本、版本编码、说明、时间及完整包引用必须一致；只有协议 2 增加 `manifest:{url,size,sha256}`。清单摘要和完整包摘要都受既有 Ed25519 签名保护。

公开 `/api/v1/launcher/application` 默认返回协议 1；明确请求 `?updaterProtocol=2` 且该发布具备增量清单时才返回协议 2。原客户端仍能通过完整包升级，新客户端也接受历史协议 1。现有数据库列继续保存发布 JSON，不迁移账号或其他业务表。

## 发布原子性和存储

后台仍选择一个完整 ZIP 和一个版本 JSON。发布 API 先验证两个信封、原有 OSS 地址及 ZIP 摘要；对协议 2 额外验证 ZIP 内清单与签名摘要一致、文件路径/大小/哈希/重复项/总量，然后按文件内容摘要生成复用对象，并上传签名引用的清单。所有对象就绪之后才执行原有管理员鉴权、乐观版本与幂等发布事务。准备失败不改变当前可见版本。

固定对象路径均在原 OSS 中：完整包 `launcher/application/windows-x64/<sha>.zip`；原始文件 `launcher/application/windows-x64/files/<sha>`；清单 `launcher/application/windows-x64/manifests/<sha>.json`。文件对象不可变、可被多版复用，不按单个版本随意删除。上传采用传输校验，客户端仍独立执行 SHA-256 校验。

文件清单限制 20,000 项、8 MiB 文本、4 GiB 展开大小，禁止重复/冲突路径、链接、目录项及程序之外的配置、账号、游戏、Java路径。增量准备使用独立发布互斥和有界工作数，不占用长期数据库连接，不重启游戏服。

## 客户端行为及验收

客户端先验证签名与清单，再按本地实际文件哈希复用；缺失/损坏文件重新下载，新增文件进入暂存区，废弃受管文件按旧清单清理。网络不可用或增量流量大于完整 ZIP 时可选择独立验证的完整包；签名、路径或内容篡改不得被当作普通网络故障忽略。校验完成后沿用事务备份/恢复，个人数据保持。

验证旧请求得到原格式、新请求得到协议 2、不同版本/包引用无法配对、权限和幂等保持、对象或清单不完整不得发布；使用本机隔离数据库和假 OSS 验证完整发布路径。最终需记录正式构件、真实字节量、增量/完整包兼容安装与失败恢复证据，候选不能提前称为上线。
