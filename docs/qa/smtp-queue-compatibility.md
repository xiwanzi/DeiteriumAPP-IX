# SMTP 队列与线上数据库兼容性修复

2026-09-13。用户反馈管理后台发送测试邮件失败，并计划后续给白名单审批通过接入邮件；审批邮件正文尚未确定，本轮先修复已有发送通道。

## 实际故障

线上数据库是 MariaDB 10.5.29。邮件工作器领取任务的查询使用 `FOR UPDATE SKIP LOCKED`，线上原句返回 1064 语法错误，失败发生在领取任务之前，所以记录长期为 `PENDING / attempts=0`，界面没有投递错误。原工作器遇到这个错误直接跳出本轮，也没有日志。

首次检查还发现 SMTP 端口 465 搭配 STARTTLS，收件人填成 `4897111929@qq.com`。随后用户确认测试应发送至 `489711929@qq.com`，后台已保存为 TLS/465 与该收件人（设置版本 8）。从生产服务器以 Go 与保存的加密授权码认证 QQ SMTP，结果成功，没有发送消息；不需要更换密码。

## 修复与验证

使用普通 `FOR UPDATE` 领取任务，沿用短事务、发送租约与尝试次数校验；服务本来就只有一个邮件工作器。数据库错误等非空队列错误写入结构化日志，空队列和主动取消不产生警告。

- 在实际 MariaDB 10.5.29 的随机隔离数据库运行修复后的领取/完成函数，验证领取成功、未过期租约不重复领取、已完成任务不再领取；隔离数据库已删除，未触碰生产业务表。
- 新增并发领取不同任务、租约过期恢复、旧发送者不能完成新租约的集成测试。
- 继续验证原来的设置加密、版本与请求幂等、发送失败持久重试，以及通知与业务事务一同提交/回滚。
- 上述 3 项数据库集成测试以 `-race` 通过，通知模块测试及 vet 通过。实际发布后两封已排队的测试邮件均被 QQ SMTP 接收，详见[上线记录](../deployment/smtp-queue-fix-live.md)。

白名单审批通过当前还没有邮件入队逻辑。本轮没有代写或启用未确定的通知正文，也不会把旧白名单重置或管理员手动添加冒充为新申请审核通过。后续应复用已修复的 SMTP 通道，在审批事务中为该申请记录一次通知，并明确接收邮箱和发送内容。
