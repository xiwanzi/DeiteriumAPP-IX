# 真实订单与委托本机验收

2026-09-08，验证对象：`test-release-v2/backend-next` 的 `commerce_v2`、商品成交模板冻结，以及扩展后的 App OpenAPI。数据库为本机回环 MariaDB；每项测试只创建并清理自己的随机测试库。资金和 Mail RPC 使用遵守原键幂等、独立维护累计余额的可控执行器；没有从测试向实服转账或发送物品。

## 已实现

- 创建订单重新验证本人报价、公开商品版本、价格、库存和交付范围；产品发布时冻结完整模板内容，后续模板编辑不改变该公开版本的交付。订单保存原物品版本、数量、摘要、唯一 deliveryId、收件人和领取服务器。
- 市场/委托预付到 DaoYu，固定卖家或唯一接取者为受益人；官方邮箱确实 CLAIMED 后结算 DIMA。退款只回原付款者；XConomy 原操作金额为零的查询记录不能充当某次支付证明。
- 持久操作、逐步执行、租约、明确失败恢复、UNKNOWN 原操作查询；不在 SQL 锁内调用 Core，不可用时不排队新付款。事务冲突只重跑已回滚的数据库意图事务。
- 一次退款机会，父交易版本与嵌套退款版本分开；拒绝/撤回恢复原剩余时间。普通商品 72 小时确认，委托完成后独立 72 小时验收；未完成工程不会被到期扫描结算。
- 介入暂停、冻结证据与消息引用、管理员分配、部分退款后余款结算，任一步未知或失败保留原进度。已转出资金不能伪造追回；仍有在管冻结款不能用“人工追回”关闭案件。
- 官方退款先完成严格撤回；NOT_FOUND、UNKNOWN 和身份/摘要/范围不匹配都不能解锁退款。未创建邮件必须有 API 2 的 CANCELLED_BEFORE_CREATE 墓碑；取消时间为 Unix 秒。失败撤回后迟到的 CLAIMED 会拒绝原退款并放行一次 DIMA 结算。
- 完成凭证图片和介入证据经过业务权限校验后签名；Order/Commission/Case 带跨设备查询原操作、原案件的权威引用。通知和事件与交易同事务保存，按参与者隔离。

## 验证结果

1. 联合回归：`go test -race -tags integration ./internal/httpapi ./internal/store -run 'Commerce|Catalog' -count=1` 通过；包含该工作区的 HTTP 路由、Core 适配器、目录、交易和四角色介入测试。
2. 后续复核修正的针对性命令 `-run 'TestCommerce(Unlimited|LateClaim|InterventionPartial|MailCreate|Cancellation)'` 通过；重建 Server 后的迟到领取/到期恢复另单独复验通过。
3. 本轮金融测试文件含 13 个集成测试：12 路同键提交/派发只产生一个扣款；两买家争一份库存仅一方成功；明确扣款失败恢复库存；不限量订单切回有限库存后失败不凭空增加库存；未知原键恢复、零金额假证明拒绝；唯一委托接取、失败/未知绑定恢复；取消/原路退款；退款次数/嵌套版本/暂停恢复；部分退款成功但余款结算失败后只补余款；官方模板冻结/领取结算；缺失邮件取消证明；后台公平性与迟到领取恢复。
4. 三个证明单测逐字段破坏资金回执、取消身份/域/节点/摘要/时间/证明类型，以及 mailbox.create 的 UNKNOWN 收据，均不能推进成功。
5. 后台公平性测试各放置 21 条阻塞记录和第 22 条有效记录，验证 pending 租约、未完成施工与未变化邮件回执均在 SQL LIMIT 前过滤，不堵塞后面的工作。
6. 通过真实 HTTP 路由生成 9 类响应，再用 `scripts/validate_contract.py` 和扩展 OpenAPI 校验：订单创建/详情/快照/退款、委托创建/详情/快照、操作查询、介入详情。保存的都是隔离测试身份和资产引用。
7. `go vet ./internal/store ./internal/httpapi` 与本轮文件 `git diff --check` 通过。

报价阶段补充复核：模板单件 40/maxQuantity 64 的商品买 2 件、两个商品各买 1 件聚合超量、两家店、两个库存域及同域但领取服无交集，现在都在报价阶段拒绝，不生成资金意图。独立复现改为 `catalog_v2_quote_integration_test.go` 的永久回归；商品公开版本、库存、归档与原图绑定检查仍保留。报价与下单共用聚合实现，013 无变化。
