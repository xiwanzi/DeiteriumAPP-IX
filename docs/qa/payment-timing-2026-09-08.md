# 支付动画时序核对

2026-09-08。用户询问额外约半秒的转圈是否来自后端等待，以及能否在 1–3 秒模拟识别期间提交请求。以下为代码核对，不是网络时延实测。

[PaymentExperience.kt](../../android-app/ui-lab/src/main/java/com/deuterium/app/uilab/PaymentExperience.kt) 当前顺序为：
1. 等待随机 1000–3000 毫秒的模拟识别。
2. 再等固定 470 毫秒（关闭动效时为 100 毫秒）。
3. 才调用 onCommit，转账等调用方在其中发起真实业务请求。
4. 真实结果返回后才退出等待状态。

[PaymentConfirmation.kt](../../android-app/ui-lab/src/main/java/com/deuterium/app/uilab/PaymentConfirmation.kt) 在 waiting 状态循环播放第 9–21 帧，每轮 400 毫秒。返回结果后从当时的帧继续到确认勾，再分别等待 140 毫秒、130 毫秒触发反馈与完成；自动关闭另有 850 毫秒。这些都是前端时序，不能据此把用户看到的额外时间当作网络 RTT。

可行优化是用户已经明确确认付款后，并行执行模拟识别和原幂等付款请求；识别结束且结果确认后衔接对勾。网络较慢或结果未知时仍要等待/恢复，不能只因动画计时结束就报成功，也不能因页面重建重复提交。

本次用户将此作为疑问，20101 没有更改付款请求时序、资金状态或结果恢复逻辑。
