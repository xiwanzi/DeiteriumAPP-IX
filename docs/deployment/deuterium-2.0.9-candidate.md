## 获得本轮发布授权后的顺序

1. 核对发布期间的新订单/领取/委托与配置，保留原真实数据；记录当前在线节点、包版本及配置摘要。
2. 将主仓库和独立 Mail 的准确源码分别推送、审阅并合并；重新核对发布包与合并代码一致。
3. 做一致性备份：后端、Mail、XConomy 数据库，以及现有配置、插件、Web 指向与更新清单。只备份，不恢复或初始化业务。
4. 协调游戏服务维护窗口，更换配套 XConomy/Core/Mail/Bridge。沿用 MEK 的停止/禁领状态；避免新旧经济写入实现混跑，不热重载。
5. 用数据库维护连接执行新增 `023_commerce_promotions.sql`。后端运行账号不增加 DDL 权限。确认 Mail API 3/creditRewards 能力和已有实物邮件可读。
6. 发布配套 Go/Web，检查当前商品、订单、购物袋、券权限与额度规则；通过后再切换 20900 的 APK 更新清单。更新公告/主动账号提醒按用户本轮要求执行。
7. 检查真实游戏客户端的 TACZ 附件预览与信用点领取，再记录实际公网、原生安装和运行状态；没有实测的内容不填写为通过。

## 回退

发布前保留当前二进制、插件和网页目录。若中途未就绪，停止接受新促销/信用点订单，回到已验证的服务与页面；保留所有新增订单、券占用和数据库表。涉及已创建的新型邮件时保留兼容 API，先完成或安全取消相关交易，再决定是否回退插件。

不得整库恢复覆盖新增业务，不从“查询不到”推断可以退款，不更换未知结果的请求键。已安装 20900 不自动降级；客户端修正需要更高版本号。具体状态机和兼容约束见[增量契约](../contracts/commerce-promotions-v209.md)。

本轮完整验证见 [QA](../qa/commerce-v209.md)。
