## 接入方案建议

| 对象 | 正式入口 | 备案期间测试入口 |
| --- | --- | --- |
| 玩家网页 | `https://chat.deuteriumix.com/` | `<协议>://<服务器IP>:<网页端口>/` |
| 官方管理端 | 建议使用同站 `/admin` | 同一网页端口下 `/admin` |
| App API | `https://api.deuteriumix.com/api/v1` | `<协议>://<服务器IP>:<API端口>/api/v1` |
| 浏览器业务请求 | 建议使用本站相对路径 `/api/v1`，由网关转发同一个后端 | 同样使用相对路径，减少迁移改动 |

以上 `/admin` 和网页网关是建议，不是用户已指定的路由。网页与 App 共用业务后端、账号、账本、状态机和幂等规则。更换域名不复制数据或接口；IP 站点的浏览器登录和推送订阅不自动迁移到域名站点，切换后重新登录、重新订阅。

建议现有登录、退出、当前用户接口支持网页 Cookie 会话及 CSRF 防护；Android 保留 Bearer。不改用 JWT 或新增独立账号系统。网页 WebSocket 支持同站 Cookie 并校验 Origin，避免额外票据接口；若最终选择浏览器直接携带 Bearer，则另定一次性 WebSocket 票据协议。网关必须传递 Set-Cookie、WebSocket 升级与 AI 流式响应，并禁止共享缓存私有业务结果。

IP＋端口不等于只能使用 HTTP。真实账号和管理操作测试优先配置浏览器信任、与 IP 匹配的 HTTPS。公网 IP 的普通 HTTP 页面不属于安全上下文，不能完整验证 Web Push/Service Worker，也不能按正式方案验证 Secure Cookie；普通 HTTP 不作为真实密码与管理凭据的正式传输方案。不能通过全局关闭证书检查解决。参见 [MDN 安全上下文](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)及 [Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)。

生产服务器测试前核实已有监听、代理和插件桥配置，再选择端口。沿用受控插件桥边界，不把桥端口作为网页/API 公共端口。此处没有授权立即改动生产配置或对真实账号执行封禁。

## 封禁管理建议新增接口

下列路径统一以 `/api/v1` 为基础路径，是待审定的增量草案，不计入当前 OpenAPI 已有操作数。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /admin/players` | 分页搜索注册账号，支持账号状态筛选；不扩大普通玩家目录权限 |
| `GET /admin/players/{playerRef}` | 查看管理用账号资料、当前封禁及未完成交易数量；禁止返回密码、令牌 |
| `GET /admin/players/{playerRef}/bans` | 分页查询封禁、到期与解封历史 |
| `POST /admin/players/{playerRef}/bans` | 封禁账号，记录原因、期限和操作者 |
| `POST /admin/players/{playerRef}/bans/{banId}/revoke` | 有理由地提前解封，保留原始记录 |
| `GET /admin/players/{playerRef}/open-transactions` | 分页列出需处理的订单、委托、退款、资金未知操作及关联案件；限获授权管理员 |
| `POST /admin/interventions` | 管理员依据封禁记录主动创建交易处理案件；复用现有案件详情、领取、裁决与审计接口 |

字段建议：`banId`、`playerRef`、`reasonCode`、对本人展示的 `reason`、管理端 `internalNote`、`startsAt`、`expiresAt`、`status`、操作者、解除原因及时间、`version`。建议支持限时及永久封禁（`expiresAt=null`），首版立即生效，不引入预约封禁。写入沿用 `clientRequestId` 和 `expectedVersion`，禁止同键不同正文、并发重复封禁或重复解封。

权限建议分为账号查询、封禁、解封、交易接管；普通商家权限不自动包含封禁。禁止自封及绕过权限管理高权限账号；管理员之间的操作层级需在详细契约中明确。复用 `/admin/audit-events`，审计保留前后状态、理由、操作者与请求标识。

## 封禁执行边界

1. 封禁是服务端账号级限制，不能只隐藏按钮或只拦网页。后端现有 `Users.status` 与会话有效性检查可以作为基础，但没有据此认定已具备完整封禁能力。
2. 封禁成功后阻止 App 和网页登录，撤销全部相关 App/Web 会话，关闭旧 WebSocket/流式连接；后续消息和业务动作仍须重新校验账号状态。解除封禁不复活已撤销令牌，用户重新登录。
3. 改密、重置密码、刷新页面和使用旧客户端不能清除封禁。封禁绑定已有权威账号/服务器 UUID 关系，不依赖可改显示名；不增加 IP 连坐封禁。
4. 登录校验凭据后才能向本人返回封禁原因、到期时间及联系处理说明，不能通过公开账号查询泄漏封禁记录；内部备注只对授权管理者可见。
5. 暂不调用游戏 ban/kick 命令，不改变玩家进入 Minecraft 的权限。游戏邮箱真实领取状态仍由插件回传，不能因 App 封禁伪造为未领取。
6. 限时封禁采用服务端时间；到期检查需可在重启后恢复。封禁与高风险写操作并发时，未提交操作须检查最新限制；已经提交的资金操作保留原幂等标识并查证结果。

## 未完成交易的接管建议

用户已确认由管理员处理。以下具体规则为建议，需作为下一轮详细契约的一部分明确：

- 封禁不删除订单、聊天证据、账本或历史，不直接没收余额，不自动对所有交易退款。
- 建议暂停被封账号的新增发布、接取与购买，并将其在售商品和待接取委托移出公开入口。待接取委托的预付款进入管理处理队列，不静默丢失；解除封禁后不自动恢复商品上架。
- 建议封禁生效时将相关未完成交易可靠登记为待处理；对会因该账号无法确认而影响双方权益的自动验收计时，建立受控暂停。暂停与定时结算必须互斥，不能先返回已暂停、实际资金却已释放。封禁与接管登记应具有事务或可恢复执行保证。
- 不盲目停止已发出的经济指令。扣款/发货/退款结果未知时先按原 operationId/deliveryId 查询；封禁不是重复扣款、重复退款或重复发放的理由。
- 管理员主动开案使用 `source=ACCOUNT_BAN`、`banId`、交易类型/ID、原因、幂等键和版本；服务端取得权威快照。该来源不要求被封用户先登录申请，也不要求退款已经被拒，须有独立管理权限并审计。
- 一个交易最多一个活跃案件；已有案件返回或关联原案件，保留原证据。订单另一方只能读取自身交易可见信息，不获得封禁内部备注。
- 接管复用现有资金裁决边界：未释放担保可按核准规则退款/释放；已结算款项不能任意扣成负数。案件保持处理中直到真实资金回执完成。商城是否可退仍以邮箱领取/撤回互斥结果为准。
- 被封用户不能依赖登录后的申诉页求助。首版可在凭据验证成功后的封禁提示中显示运营方配置的联系渠道；不默认开放匿名上传或另建账号封禁申诉系统。交易申诉与账号封禁异议分别处理。

## 延续上轮接口差异评估

- 商城、市场、委托、聊天、钱包、官方商品、争议裁决等继续复用现有契约。
- 建议为玩家申诉中心增加 `GET /interventions`；现有单案件查询/补证/撤回继续复用。
- 公告素材扩展 `/assets` 的用途与权限，避免把平台公告强行绑定官方店铺。
- 若包含网页关闭后的系统通知，扩展 Web Push 订阅/注销及公钥配置，保留现有站内通知接口；普通 HTTP IP 测试不能作为这项验收。
- 管理页面可以展示更多筛选、完整条款、处理时间线、证据和审计记录；仅新增后端确实缺失的数据读取/动作，不按页面重复设计业务 API。
