# 测试版真实订单与委托编排

2026-09-08。依据本轮用户确认，在 `test-release-v2` 实现 App/Web 共用交易；Core 执行器和 MC/Linux 部署由主任务对接。目录已独立交付，本文覆盖后续 013 及 `commerce_v2` 范围，不修改已部署迁移。

## 已确认的资金与身份边界

- 信用点权威仍是 MC XConomy/Vault 路线。DIMA 是官方商城收入专户，DaoYu 是冻结资金专户，**这不是烧币**。
- 所有预付由原付款玩家转至 DaoYu；市场结算付固定卖家，委托结算付事务中唯一接取者；官方订单领取后由 DaoYu 转至 DIMA；退款只回原付款者。
- 预付、绑定受益人、结算、退款分别使用 Core 固定白名单命令。已登记的业务引用、付款人和金额不可变。委托预付时未指定 worker；接取事务锁定唯一候选后，通过幂等 bind 完成一次受益人绑定，未确认的 bind 不允许换人重接。
- 客户端不能指定付款 UUID、实际卖家、专户、冻结余额或直接支付金额。它只能引用自己的有效报价或提交已校验委托内容；服务端读取身份和商品快照，锁定参与者/库存后生成执行计划。

## 持久化与恢复

013 保存交易、不可变快照、退款、操作计划和执行步骤、状态事件及介入案件。SQL 事务只处理数据库，不跨网络长期持锁。任何发往 Core 的步骤在发送前已记录稳定 clientRequestId；短租约阻止 HTTP 与后台同时派发。

Core 不可用时拒绝新付款，既不扣库存也不排队待恢复。已开始的操作可在恢复后按原步骤继续；结果 UNKNOWN、网络超时、丢回包均不能新建一笔扣款或退款。已知 Core operationId 时 Query；响应丢失尚未知 ID 时，按同 actor/clientRequestId 的幂等 Execute 找回已持久操作，不改变业务内容。

COMPLETED 必须带原业务/冻结引用、金额/币种及固定参与者证明；不接受空成功状态。只有可靠 FAILED 且未产生副作用才能释放库存或恢复前一状态；任一部分已执行或无法证明时保持冻结/UNKNOWN，保留原步骤对账。

## 订单与委托

- 创建订单重新核对报价所有者、期限、版本、每个产品的当前公开版本/价格/库存和交付条件，固定快照；并发库存只有一方能占用。报价本身不预留库存。
- 报价与下单共用整单交付聚合：同店、同背包域、领取服务器交集、每个精确物品版本累计数量上限，以及受控资金金额上限。不产生“报价成功但同样条件下必定无法下单”的付款引导；模板按唯一引用排序加锁。
- 市场未发货不能确认；普通商品发货后 72 小时自动确认。建筑从开始施工计算总工期，提交完成不重置；只有已经完成的工作进入验收结算，未完成过期不冒充交付。
- 委托预付成功才公开 OPEN；自己不能接自己的委托，只能一名玩家成功接取。接取/受益人绑定确认后开始工期；提交完成后独立 72 小时验收。工作逾期只标明逾期，不自动结算未完成工作。
- 自动验收由服务端周期处理并在重启后补算。后台与用户确认、退款及平台案件用同一交易行/版本互斥；自动动作也有稳定操作键。
- 官方商品仅用已批准的模板与冻结物品版本/摘要构造 MailboxIntegration 快照，不发任意命令/NBT。预付后创建独立邮箱交付；退款必须先严格撤回，已领取/领取中/未知不能退款。领取证明与原订单/收件 UUID/快照摘要匹配后才结算 DIMA。

## 退款、介入与通知

每笔交易只有一次退款机会。未发货/未接取的明确取消使用原路退款；已开始履约需对方处理。请求使用父交易版本，处理/撤回使用嵌套 refund.version，并始终锁父交易。拒绝必须有原因，撤回/拒绝不恢复次数。

退款和平台受理暂停当前剩余期限；拒绝/撤回后恢复剩余秒数，不重置 72 小时。已完成结算不能通过普通退款入口重新返款。介入案件 ID 写入权威 OrderView/CommissionView 的 `interventionCaseId`，供另一设备恢复案件；资金已结算时只能要求人工处理，不能凭备注伪造追回。

部分退款与余款结算采用两个持久步骤，前一步确认后才执行后一步；其间失败/断线保持 RESOLVING，禁止其他自行结算。通知和状态事件在业务事务内落盘，按固定接收者隔离，不将订单或私聊细节广播公共频道。

## 验证与交付

使用隔离 MariaDB 和可控幂等执行器测试库存/接取并发、同键与冲突重试、失败/超时/断线、退款次数、嵌套版本、确认/退款/到期互斥、暂停恢复、重启补算、固定收款方、跨用户权限、快照不变与介入跨设备恢复。再由主任务用真实 Core、两个授权游戏身份和服务端账本验证；注入执行器通过不能冒充实服资金已通过。
