# Android Gradle APK Builder

## Core Rule

Treat every Android project as unknown until inspected. Do not assume module name, task name, output path, SDK path, signing setup, or version source of truth.

## Workflow

1. Locate the Gradle root by walking up to `settings.gradle`, `settings.gradle.kts`, or the nearest Android `build.gradle(.kts)`.
2. Run the read-only doctor first:

   ```powershell
   .\scripts\android-build-doctor.ps1 -ProjectDir <project-or-subdir> -Json
   ```

   Add `-ListTasks` only when task selection is unclear or the user asked to build.

3. Identify Android application modules. Prefer modules using `com.android.application`; do not build libraries as deliverables unless the user asks for an AAR.
4. Choose the build target from discovered tasks:
   - Use debug APK for a normal update-install or testable handoff.
   - Use flavored debug tasks such as `assemblePaidDebug` when flavors exist and the user selected a flavor.
   - Use release only when signing is configured or the user explicitly accepts unsigned/release build limitations.
   - Use bundle tasks only when the requested artifact is an AAB.
5. Build with the project wrapper when present. Use system `gradle` only if no wrapper exists and the user accepts that fallback.
6. Locate outputs by scanning `**/build/outputs/apk/**/*.apk` or `**/build/outputs/bundle/**/*.aab`; do not hard-code `app/build/outputs/apk/debug/app-debug.apk`.
7. Verify the artifact before delivery:

   ```powershell
   .\scripts\verify-apk-version.ps1 -ApkPath <apk-path> -Json
   ```

8. Report the exact command run, artifact path, package name, `versionCode`, `versionName`, and any install risk.

## Version Bumps

Only bump versions when the user asks for an update-installable or release-ready artifact. First identify the source of truth:

- Direct values in `build.gradle` or `build.gradle.kts`: edit that file.
- Values in `gradle.properties` or `libs.versions.toml`: edit the referenced source.
- Values generated by CI, Git tags, `buildSrc`, convention plugins, or custom Gradle code: stop and explain the source before changing anything.

For update installs, increase `versionCode`. Change `versionName` only when the user asks or the project convention clearly ties it to the build.

## Failure Handling

Classify failures before changing code:

- Read [troubleshooting.md](references/troubleshooting.md) for SDK, JDK, AGP, Kotlin, dependency, signing, and install errors.
- Read [android-gradle-build-workflow.md](references/android-gradle-build-workflow.md) when project shape, variants, version source, or artifact selection is ambiguous.

## Guardrails

- Do not modify backend, server plugins, API contracts, keystores, signing passwords, or unrelated source files.
- Do not delete Gradle caches, build outputs, or local files unless explicitly requested.
- Do not commit `local.properties`, keystores, tokens, or machine-specific secrets.
- Do not present a build as successful until the final artifact path and APK metadata are verified.
